# mcprod

`mcprod` is the production-core command line interface. It prepares
reproducible runtime releases, freezes bounded CERN runs, exports explicit
CERN-to-IHEP handoffs, prepares resumable IHEP batches, and runs aggregation
from validated products. Commands print a JSON summary and accept
`--log-level {debug,info,warning,error}`.

Run it from this checkout with `./mcprod`. An installed checkout also
provides the `mcprod` console script.

For pilot operations, use `docs/testing.md` as the procedure and this page as
the command/lifecycle reference. Check these before querying CLI help; if a
verified command or option is missing or stale, update the docs after checking
the parser/source.

## Run lifecycle

Start by listing the physics catalogue:

```bash
./mcprod catalog
```

A wrapper workspace keeps campaign specifications, production history, ignored
working files, and runtime releases around this core. Initialize one after the
core revision is committed:

```bash
./mcprod workspace init --directory /path/to/production-wrapper --core "$PWD"
```

A campaign specification is a JSON object with a path-safe `run_id`, a finite
`sources` inventory, and one or more campaign entries. Each source either
has a counted existing LHE URL and `actual_events`, or a finite generation
`max_events`. Each campaign declares its analysis, source slots and finite
`target_mixed_events`, `max_processing_nodes`, and `merge_events`. Start
from `campaigns/example.json` generated by `workspace init`, then replace
its example source and limits.

Prepare a runtime release before planning. Select the site and release name
explicitly; the planner checks the release descriptor and profile assets:

```bash
./mcprod runtime prepare --site cern --release production-v1 \
  --output-dir /path/to/production-wrapper/runtimes/production-v1/cern
```

Freeze and prepare a bounded CERN run without submitting it:

```bash
./mcprod run plan --spec /path/to/campaign.json \
  --output-dir /path/to/production-wrapper/work/example/cern \
  --log-level info
```

Use `run status`, `run submit`, and `run resume` with
`--run <run-directory-or-id>` for the recorded CERN run. Submission records
the schedd and root DAGMan ID; resume targets that exact run.
Before `run submit`, `mcprod` checks the X.509 proxy paths pinned in the worker
submit files with `voms-proxy-info --timeleft`. Every proxy must have more than
48 hours remaining. A failed check stops before storage reservation or Condor
submission; `run resume` does not repeat this check. Refresh the pinned proxy
path before the first submission.

### Resuming a stopped CERN run

Use `run resume` only for a run that already has a recorded submission, a
known terminal root DAGMan state, and a root rescue file. It reads the
recorded scheduler from `submission.json`, selects the latest
`run.dag.rescueNNN`, creates a new submission attempt, and preserves nodes
already recorded as successful. It does not migrate the run to the current
`myschedd` selection and it does not replace an ambiguous submission.

The `--run` value can be the actual run directory or a wrapper run ID. For an
AFS run directory, use the directory itself so the CLI does not append the
site path a second time:

```bash
RUN=/path/to/production-wrapper/work/example/cern
LOGDIR=/path/to/production-wrapper/operator-logs
mkdir -p "$LOGDIR"

# Refresh and check the proxy pinned in the generated submit files first.
voms-proxy-info --file /path/to/x509_proxy --timeleft
./mcprod run status --run "$RUN"
ls -l "$RUN"/run.dag.rescue*

./mcprod run resume --run "$RUN" \
  | tee "$LOGDIR/resume-$(date -u +%Y%m%dT%H%M%SZ).json"
python3 -m json.tool "$RUN/submission.json"
```

After recovery, take a fresh exact-root snapshot using the scheduler and root
cluster from the new `current_attempt` in `submission.json`. Do not call
`condor_submit_dag` directly, retry `run resume` after an ambiguous result, or
use `myschedd bump` to move an existing run.

The operational command map is:

- `runtime prepare` pins a clean site-specific runtime release.
- `run plan`, `run status`, `run submit`, and `run resume` manage one CERN run.
- `handoff export` and `handoff transfer` advance a completed CERN run to IHEP.
- `batch prepare`, `batch status`, `batch submit`, and `batch resume` manage
  the IHEP batch associated with that handoff.

Export a ready component handoff, transfer it with the site configuration, and
prepare one combined IHEP allocation per merge group:

```bash
./mcprod handoff export --run /path/to/production-wrapper/work/example/cern
./mcprod handoff transfer --run /path/to/production-wrapper/work/example/cern \
  --site-config /path/to/production-wrapper/sites/ihep.json
./mcprod batch prepare --handoff /path/to/handoff.json --output-dir /path/to/batch \
  --runtime-dir /path/to/matching-ihep-runtime \
  --proxy /path/to/x509_proxy --log-level info
```

Inspect or reconcile a prepared batch using its manifest:

```bash
./mcprod batch status --manifest /path/to/batch/batch_manifest.json
./mcprod batch submit --manifest /path/to/batch/batch_manifest.json
./mcprod batch resume --manifest /path/to/batch/batch_manifest.json
```

`batch submit` checks the proxy source recorded in each prepared worker wrapper
before submitting any HepJob jobs. Each distinct proxy must have more than
48 hours remaining; `batch resume` does not repeat this check. When a wrapper
uses `X509_USER_PROXY`, set that variable to the intended proxy before the
initial `batch submit`.

An ambiguous HepJob submission is retained as an unresolved attempt. Reconcile
the exact recorded job before resubmitting.

## Aggregation

Aggregation is a separate preparation and worker step. It accepts validated
selection and efficiency-shard pairs from a handoff, and publishes selected
ROOT output plus an efficiency-map tar per sample:

```bash
./mcprod analysis aggregate --run /path/to/production-wrapper/work/example/cern \
  --prepare --handoff /path/to/handoff.json --output /path/to/aggregation.json \
  --campaign JJP --log-level info
./mcprod analysis worker --task /path/to/aggregation.json \
  --work-dir /path/to/aggregation-work --log-level info
```

Selection and efficiency both consume the full raw ntuple. Aggregation rejects
unverified, duplicate, malformed, or overlapping inputs.

## Worker and internal commands

The public worker adapter runs a single staged task:

```bash
./mcprod worker --task task.json --work-dir worker-output
```

`internal advance-wave` is used by generated DAGs to commit the next bounded
controller transition. It is not a replacement for the run lifecycle commands.
